How OrderSummary is built

OrderSummary looks like a table, but you never INSERT or UPDATE it by hand. It is derived state — a read model re-computed by replaying an append-only log of order events through pure handlers. This page shows how.

1 · The pipeline

The event log is the source of truth. To change state you append an event; to read state you replay the log into OrderSummary. Replay is idempotent, so re-running it converges to the same rows.

flowchart LR E["order event
(a dict)"] -->|append| S[("orders stream
append-only log")] S -->|replay| U["upcaster
qty → quantity"] U --> H["versioned handler
event → Effect"] H --> X{"DjangoExecutor"} X -->|update_or_create / update| P[("OrderSummary
read model")]

2 · An event is not a row

A handler is a pure function: it takes one (already-upcasted) event and returns an Effect — a description of a write, not the write itself. The DjangoExecutor applies it. That's what makes handlers trivially testable and replay-safe.

{% verbatim %} 
# event in the log                         # Effect the handler returns
{                                          Effect(
  "order_id": "ORD-1003",                    op="update_or_create",
  "status": "PAID",                          model_label="orders.OrderSummary",
  "items": [                                 lookup={"order_id": "ORD-1003"},
    {"sku": "KETTLE-STEEL",                  defaults={
     "quantity": 1, "price": "40.00"}         "status": "PAID", "subtotal": 40,
  ]                                            "tax_rate": 0, "tax": 0, "total": 40,
}                                            },
                                           )

3 · Versioned handlers — why tax flips at seq 3

The sales-tax rule changed at one point in the log (TAX_CHANGE_SEQ = 3). Two versions of the same handler are registered; the event's seq (its position in the stream, not its order number) selects the version that was in effect then. Replaying an old event still uses the old rate — the fix-forward never rewrites history.

flowchart TD A["event at seq n"] --> B{"n < 3 ?"} B -->|yes| V1["order_totals v1
rate = 0%"] B -->|no| V2["order_totals v2
rate = 10%"] V1 --> R["tax = subtotal × rate
total = subtotal + tax"] V2 --> R
{% verbatim %} 
@register_handler(name="order_totals", effective_from=0, effective_to=TAX_CHANGE_SEQ)
def order_totals_v1(event):        # seq 0,1,2
    return _totals_effect(event, Decimal("0"))          # 0% tax

@register_handler(name="order_totals", effective_from=TAX_CHANGE_SEQ, effective_to=None)
def order_totals_v2(event):        # seq 3, 4, 5, ...
    return _totals_effect(event, GST_RATE)              # 10% tax

def _totals_effect(event, rate):
    subtotal = sum(Decimal(i["price"]) * i["quantity"] for i in event["items"])
    tax = (subtotal * rate).quantize(Decimal("0.01"))
    return Effect(op="update_or_create", model_label="orders.OrderSummary",
                  lookup={"order_id": event["order_id"]},
                  defaults={"subtotal": subtotal, "tax_rate": rate,
                            "tax": tax, "total": subtotal + tax, ...})
{% endverbatim %}

4 · One row, several owners

A single OrderSummary row is assembled by three independent handlers, each owning a disjoint set of columns. check_disjoint_defaults rejects any batch where two handlers write the same column, so ownership stays clean.

flowchart LR H1["order_totals"] --> C1 H2["order_loyalty"] --> C2 H3["order_bonus"] --> C3 subgraph ROW["one OrderSummary row · keyed by order_id"] C1["status, subtotal,
tax_rate, tax, total"] C2["loyalty_points"] C3["bonus_points"] end
ColumnsOwnerEffect opValue
status, subtotal, tax…order_totals update_or_create computed from the order's items
loyalty_pointsorder_loyalty update_or_create 1 pt per $ of subtotal, PAID only
bonus_pointsorder_bonus update carried on a separate bonus event

5 · op="update" — update-if-exists

order_totals and order_loyalty use update_or_create because they legitimately create the order's row. But a loyalty bonus is a secondary owner: it should decorate an existing row and never mint one. That's exactly what op="update" does — filter(...).update(...), which updates in place and is a no-op when nothing matches.

flowchart TD B["loyalty_bonus event
{order_id, bonus}"] --> Q{"row for
order_id exists?"} Q -->|yes| U["UPDATE bonus_points
✅ lands"] Q -->|no| N["nothing matches
✅ clean no-op, no phantom row"]
{% verbatim %} 
# the handler — a secondary owner, never inserts
def order_bonus(event):
    if not _is_bonus(event):
        return None
    return Effect(op="update", model_label="orders.OrderSummary",
                  lookup={"order_id": event["order_id"]},
                  defaults={"bonus_points": int(event["bonus"])})

# the executor — update-if-exists in one line
def _update(eff):
    model.objects.filter(**eff.lookup).update(**eff.defaults)  # never INSERTs
{% endverbatim %}

On the live page, watch a bonus for a fabricated ORD-GHOST-*: the feed shows a no-op and no ghost row ever appears in the table. update_or_create couldn't express that.

6 · Putting it together

Every page here — static, live, or a migration dry-run — is the same call. Point replay at the stream and an executor; the registered handlers and upcasters do the rest.

{% verbatim %} 
from rakaia.replay import replay
from django_rakaia import DjangoExecutor

replay(store=store, stream_path="orders", executor=DjangoExecutor())
# start_seq=N replays only the tail — that's what the live producer does each tick.
# Swap in CollectingExecutor() to preview the effects without writing (a dry run).
{% endverbatim %}
